## 通读 miniweave 项目背景与架构（只读排查，未改代码）

- 定位：demo 教学项目（极小本地运行环境），从 MiniCode(MIT) 导入并重命名，目标是把 Model/Tool/Session/Permission/Context 抽成可替换插件 + 用 Benchmark/消融实验量化各机制价值。技术栈 TS + Node + Anthropic API + JSONL + git worktree。

- 实际运行时链路：bin/weave → src/index.ts（手工 new 出 Model/Permission/ToolRegistry/SubAgentManager）→ tty-app.ts(2589 行，最大文件) 或 SessionRuntime(非交互 + /goal /loop 命令) → agent-loop.ts ↔ AnthropicModelAdapter/MockModelAdapter ↔ ToolRegistry。

## agent-loop.ts 精读结论（给用户做过一次带行号的讲解）

- 定位：516 行纯函数状态机，`messages in → messages out + AgentTurnOutcome`，不做持久化、不 new 具体 model/tool；只依赖 `ModelAdapter`(types.ts:108) 与 `ToolRegistry` 两个接口 → README 说的"插件可替换"在 loop 层成立，问题只在 index.ts 装配。
- 核心机制：`messages`(真实历史) 与 `modelMessages`(每步投影) 分离，压缩不改历史（agent-loop.ts:207/242）。
- 工具批执行顺序关键（Anthropic 要求 tool_use 后必须紧跟等量 tool_result）：先按 calls 预填占位 tool_result（427-433，内容 'Cancelled before execution.'），再逐个执行按 toolUseId 回填（439-460），最后统一套预算（472-482）。大结果由 replaceLargeToolResult 落盘。
- ToolResult 里的 awaitUser/stop/fatal 让工具可以主动结束回合（tool.ts:22-29 → agent-loop.ts:461-463）。
- "让模型继续" = 追加 `{role:'user', internal:'continuation'}`（181-190），不是重发请求。
- 步数上限语义：`maxSteps` 只对 goal/loop 模式给 50（tty-app.ts:1445、index.ts:184；mode?: 'goal'|'loop' 见 runtime/turn-runner.ts:5），**普通用户对话没有步数上限**，靠"assistant 纯文本 = 回合结束"兜底。
- 发现两处死代码：`shouldTreatAssistantAsProgress`(56-74) 后三个分支全返回 false，等价于 `args.kind === 'progress'`；agent-loop.ts:416 的 `calls.length === 0` 判断在现有两个 adapter 下恒为假。

## 工具执行设计（tool.ts / tools/ 精读）

- 契约：`ToolDefinition<TInput>`(tool.ts:31-37) = `{name, description, inputSchema, schema, run}`，纯对象字面量、无基类无继承；最小完整样例见 tools/grep-files.ts(47 行)。
- **双 schema**：`inputSchema`(手写 JSON Schema) 给模型，adapter 在 anthropic-adapter.ts:334-338 写进请求体 `tools[].input_schema`；`schema`(zod) 给运行时，tool.ts:119 `safeParse`。两者并存有漂移风险（zod 有 toJSONSchema 但没走）。
- 工具有三个来源，最终都规约成同一契约：① 内置常量表 tools/index.ts:53-74；② MCP 远端 → `createMcpBackedTools`(mcp.ts:976) → `addTools` + `addDisposer`(tools/index.ts:81-92)；③ 运行时追加（index.ts:101 子 agent、session-runtime.ts:41 goal 工具）。
- `execute()`(tool.ts:106-137) 五步：find → safeParse → throwIfAborted → run → catch。**前两步失败也返回 ToolResult 而不是抛异常**（"失败即数据"）；catch 里任何异常都标 `fatal: true`（包括 abort，语义略不精确，但 agent-loop.ts:499 先查 signal.aborted 所以无影响）。
- `ToolResult`(tool.ts:22-29) 的 awaitUser/stop/fatal 让工具能影响 loop 控制流（ask-user.ts 返回 awaitUser）。
- 权限门禁在**工具内部**而非 loop：resolveToolPath(workspace.ts:11-32，无 permissions 时降级为纯路径包含检查防逃逸)、applyReviewedFileChange(file-review.ts:47-74，先 diff 再 ensureEdit)、run_command 自建三档策略(READONLY/DEVELOPMENT/未知→forcePrompt)。
- 工具批执行是**串行** `for (const call of next.calls)`(agent-loop.ts:435)，不是 Promise.all —— 避免同文件并发写冲突，代价是慢。
- 后台任务：run_command 检测 `&` 结尾 → detached spawn + registerBackgroundShellTask，taskId 形如 `shell_<base36时间>_<随机>`；存活靠 `process.kill(pid, 0)` 探测（background-tasks.ts refreshRecord），不轮询子进程。
- 可指出的不一致：`SessionRuntime.toolsFor('goal')`(session-runtime.ts:39-43) 和 `tools.subset()`(tool.ts:65-70) 都 new 出新 registry，只复制工具列表、丢掉 metadata 与 disposer。当前无实际影响（系统提示用的是 root registry 的 getSkills/getMcpServers），但是潜在陷阱。

## 简历措辞与代码核对（用户简历写"显式运行预算（模型轮次/工具调用数/总超时）"）

逐条核实结果（grep 全 src 确认）：
- ✅ "Model → Tool → Result 多轮状态推进" 成立 = agent-loop.ts 本体。
- ✅ "AbortController 取消" 成立且实现细致：turn-runner.ts:18-19 每轮建 controller 并用 `AbortSignal.any([self, parent])` 合并父信号；agent-loop.ts:156-161 包装 adapter 把 signal 织进去；abort.ts:14-29 `abortable()` 用 Promise.race 强制停止（注释明写 "even when its adapter ignores the signal"）；循环检查点 205/240/259/277/282；signal 传到工具(442)与权限(permissions.beginTurn:216)；结局转 outcome 'aborted' 而非抛异常(499/514)；子 Agent/Goal/Loop 各自持有 controller(manager.ts:50、goal/controller.ts:66、loop/scheduler.ts:127)。
- ⚠️ "模型轮次预算" 只算半成立：maxSteps 存在(agent-loop.ts:124/204)，但普通对话传 undefined = **无上限**(tty-app.ts:1445、index.ts:184)；仅 goal/loop 模式给写死的 50；子 Agent 给 MAX_SUB_AGENT_STEPS=20(agents/types.ts:3、manager.ts:146)。无配置项、无超限提示逻辑。
- ❌ "工具调用数预算" 不成立：`toolCalls` 只计数(:154/:437)并塞进返回值(:155、types.ts:68)，**全项目没有任何地方拿它跟上限比较**（唯一另一处用处是 goal/controller.ts:88 判断"这轮一个工具都没调"，与预算无关）。
- ❌ "总超时" 不成立：项目里的 timeout 全不是整轮总超时——abort.ts:38(重试退避 sleep)、agents/manager.ts:77/95(等子 Agent 30s)、loop/scheduler.ts:153(循环间隔计时器)、mcp.ts:63-64(MCP 初始化 10s/1.2s)。注意 `applyToolResultBudget`(agent-loop.ts:472) 名字像预算，但管的是工具输出占多少 token，与次数/时间无关。
- 相关背景：README 第 48 行"多 Agent 并行调度（worktree 隔离 + DAG + **预算控制**）"仍是未打勾的 roadmap 项。
